# CBACT04C modernization pilot: validation summary

**Verdict:** the Java port of `app/cbl/CBACT04C.cbl` (INTCALC monthly interest) is byte-identical
to the unmodified COBOL on all 16 scenarios, on both a frozen and the real clock, and on the shipped
`app/data/ASCII` sample. An independent Python oracle agrees with both. The documented quirks are
reproduced, not fixed. Full evidence: [`parity/RESULTS.md`](parity/RESULTS.md) (regenerated by
`parity/validate.sh`).

## Setup

Toolchain used: GnuCOBOL 3.1.2 (BDB indexed files), OpenJDK 17.0.20.1, Maven 3.6.3, Python 3.10.12, Ubuntu.

```bash
sudo apt-get install -y gnucobol openjdk-17-jdk maven python3   # skip whatever is already installed
cd modernized/cbact04c
mvn package                  # Java port + unit tests
parity/validate.sh           # the whole validation below, writes parity/RESULTS.md
```

`validate.sh` runs, in order:

1. `parity/run-parity.sh`: compiles the COBOL (`cobc -x -fsign=EBCDIC`, plus the `PARLOAD`/`PARDRVR`/`PARUNLD`
   helpers and the `CEE3ABD` stub), rebuilds the 16 scenarios, runs COBOL then Java with
   `FUNCTION CURRENT-DATE` frozen, compares record by record, and runs `oracle.py` against both.
2. `parity/run-parity-live.sh`: the same on the real clock, with `TRAN-ORIG-TS`/`TRAN-PROC-TS` checked
   for format and equality, then masked.
3. `run-sample.sh` on `app/data/ASCII` (frozen and real clock), compared with the COBOL `sample-raw` baseline.
4. `parity/check-quirks.py` on the COBOL baselines and the Java outputs.
5. `parity/mutation-check.sh`: rounding mutants of the port must all fail the comparison.
6. `mvn test`: `GoldenParityTest` replays every saved COBOL baseline, plus the unit tests.

If Maven Central returns HTTP 429, point `~/.m2/settings.xml` at a mirror
(e.g. `https://maven-central.storage-download.googleapis.com/maven2/`).

## Quirks reproduced

`check-quirks.py` asserts each one on every scenario, for the COBOL baselines and the Java port
separately (same counts on both sides):

| Quirk | Evidence |
|---|---|
| Truncation toward zero, no `ROUNDED` | all 2,272 amounts with a sub-cent remainder are cut toward zero; 1,125 of them would change under half-up rounding; 1,082 negative amounts move toward zero (e.g. `-333.33 x 9999.99 / 1200 = -2777.7472 -> -2777.74`, `-0.0099 -> +0.00`) |
| Zero-amount transaction records | 125 records of `0.00` are written, because only the rate is checked; `sample-raw` (shipped data, all balances zero) gives 50 of them and leaves every account unchanged |
| Silent overflow, no `ON SIZE ERROR` | 2 interest amounts lose their high-order digits in `S9(9)V99` (`999,999,999.99 x 9999.99 / 1200 -> 333,324,999.91`); 1 `ACCT-CURR-BAL` wraps in `S9(10)V99` |
| Last account never updated | in all 8 completed runs with category balances, the last account in key order is byte-identical to its input; in 7 of them a correct program would have changed it (e.g. account 50 in `sample-posted`). The other 1,008 accounts are rewritten as balance + interest with cycle credit/debit set to 0 |
| Category stored as `0005` | all 2,324 records have type `01` and `TRAN-CAT-CD` `0005`; `TRAN-ID` = PARM (10 bytes) + 6-digit counter |

The other quirks listed in the [README](README.md#behavioural-quirks-discovered) (misleading
missing-key messages, copy-paste open-error texts, partial output after an abend, per-record SYSOUT)
are covered by the byte-for-byte SYSOUT and ACCTFILE comparison of the `err-*` scenarios.

## Recommendation

**The approach is proven for this program and is ready to reuse on the next one.** Three independent
signals agree (COBOL, Java, oracle), the comparison is shown to be sensitive (every rounding mutant
fails), and the whole run is one command (`parity/validate.sh`).

What carries over to the next program as is: the GnuCOBOL build with `-fsign=EBCDIC`, the `CEE3ABD`
stub, the PARM driver, the loader/unloader pattern for VSAM files, `compare.py` (frozen and masked
clock), the oracle + quirk-check + mutation-check pattern, `GoldenParityTest`, and `validate.sh`.
What has to be written per program: copybook layouts (record lengths, timestamp offsets), the
scenario generator, the oracle and the quirk checks.

Before calling the port production-ready:

- **Run once on z/OS.** GnuCOBOL stands in for Enterprise COBOL. Uninitialised storage, EBCDIC/packed
  VSAM files and the real U999 abend have not been exercised. Rerunning `sample-posted` and `edge-cases`
  through the real INTCALC job and diffing against the saved baselines would close that gap.
- **Decide on the defects with the business.** The last-account bug, zero-amount records, silent
  overflow and non-idempotent restart are reproduced on purpose. Fixing any of them is a separate,
  explicit change, with the baselines regenerated afterwards.

Suggested next program: `CBTRN02C` (POSTTRAN). It runs just before INTCALC, it already runs under this
harness (`make-posted.sh` uses it to build `sample-posted`), and its output feeds CBACT04C, so the two
ports can then be checked end to end.
